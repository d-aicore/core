## Pending and handoff

Owner decisions (flags, not ratified — silence is not approval, D48/D50):

1. **BUG-SWEEP-26 policy — fresh-apply vs unswing-on-save.** Implemented policy (per dispatch): fresh-apply,
   the slot swing is re-applied to the written notes. Known limitation: `rackTemplateFromSlot`
   (`pattern_rack.cpp:481`) strips `n.extra` (removing `rackSwingBase`) but keeps the RENDERED swung ticks,
   so a template saved from a swung slot has the delay baked into its note ticks. Fresh-apply is partially
   self-protecting — `swingNote`'s grid guard (`:90-91`) skips off-grid bases at jitter 0 (e.g. a baked
   300 at swing 0.5: base 300, grid 240, diff 60 > 0 → skipped) — but with a builtin style's humanize
   jitter (fullon: 1 tick) a baked tick within the jitter of an odd 1/16 can be re-swung, doubling part of
   the delay. The alternative (unswing-on-save in `rackTemplateFromSlot`) changes saved-template semantics
   and is an owner decision; NOT pursued here. Test acceptance suggestion: save a swung slot as a template,
   load it into slots at swing 0 / 0.5 / 0.75 with and without a style, and decide the intended feel.
2. **BUG-SWEEP-28 compatibility.** Part-first changes results for templates whose row names conflict with
   destination track parts (the old name-first pick could map a bass row onto a lead track). The header
   contract is the baseline and no existing test covered `applyRackTemplate`/`matchRows`
   (`docs/contracts/core-pcore.md` is absent), so nothing green constrained the old behaviour — but songs
   that relied on it will map differently. Owner to confirm part-first as the ratified priority; the
   unambiguous cases (name-only, part-only, one row per part) are proven unchanged.

For the Test Engineer: acceptance beyond these domain tests should exercise the Windows Patterns window
(Load Template on a swung slot, then the Swing knob; a damaged `.core` with `patternSlots` of wrong types
opened in the app; a conflicting-name template import) — the UI chain (`PatternsWindow.cpp:653→667`,
`:964`) was inspected but not run, and the old throw's crash/recovery outcome is unverified. Suggested
runtime checks: `bug_tests.exe "sweep-26"` / `"sweep-27"` / `"sweep-28"` on any rebuilt tree; the builtin
case needs `pcore/styles.json` beside the sources (it fails loudly, never skips, if absent).

Residual risk: low — the swing re-application only runs when the slot swing > 0 and uses the same
`swingNote` path as the Swing knob and `rackWriteShape`; the metadata guards only widen acceptance;
the match order change is the flagged compatibility item. Kick/bass/cymbal alignment is untouched
(`pcoreApplyToSong` / align code unchanged; the swing goes on top exactly as `rackWriteShape` does).
