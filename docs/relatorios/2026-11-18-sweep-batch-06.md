Fix (`bcf9224`, `engine/src/io/device.cpp` + `tests/engine_tests.cpp` only — vendored miniaudio untouched):

- New member `normalPriority_` (`device.cpp:56`), sticky per output instance. `initContext` selects
  `ma_thread_priority_normal` when it is set, otherwise `ma_thread_priority_realtime` as before (`:116`).
- In `start()`, a platform-guarded retry (`#ifndef _WIN32`, `:183-199`): when `ma_device_init` fails and no
  fallback happened yet, log to stderr (`core: realtime audio priority refused (<reason>); reopening the device
  at normal priority (BUG-SWEEP-06)`), uninit and rebuild the context at normal priority via `initContext`, and
  call `ma_device_init` once more. If that also fails, the original error path throws as before. The guard makes
  the fallback explicit and bounded (one retry); the context rebuild uses only miniaudio's public API.
- The start result's `scheduling` field is honest after a fallback: `"normal"` instead of `"Pro Audio"`
  (`:220`). No consumer in the tree reads `scheduling` today (grep over engine/app/tests); on Windows the value
  is always `"Pro Audio"` because `normalPriority_` can never become true there.
- New regression case `tests/engine_tests.cpp:586-604` (English, +1 case / +5 verifications): the null device
  opens (`blockSize`, backend `"Null"` — `ma_get_backend_name(ma_backend_null)` —, `scheduling` present) and
  reopens; every `engine.start` makes a fresh output (`server.cpp:351`), so the second start proves each new
  output falls back cleanly on its own; `engine.stats` shows the running device; clean stop.

## Windows realtime priority unchanged (proof)

1. **Preprocessor**: the whole retry block is inside `#ifndef _WIN32` (`device.cpp:183-199`) — it does not exist
   in the Windows binary. `normalPriority_` is set true only inside that guard (`:192`), so on Windows the
   `initContext` ternary (`:116`) always selects `ma_thread_priority_realtime` and `scheduling` (`:220`) always
   reports `"Pro Audio"`.
2. **Unchanged Windows paths**: `proAudioThread()` (MMCSS "Pro Audio" + `THREAD_PRIORITY_TIME_CRITICAL`,
   `device.cpp:28-34`), `config.wasapi.usage = ma_wasapi_usage_pro_audio`, and the vendored
   `ma_thread_create__win32` (`CreateThread` + `SetThreadPriority(TIME_CRITICAL)`, result ignored,
   `miniaudio.h:16452-16464`) are byte-identical — `git show --stat bcf9224` lists only `device.cpp` (+30/−3)
   and `engine_tests.cpp` (+19). TIME_CRITICAL is privilege-free on Windows, so the open succeeds and the
   fallback condition is never reached.
3. **Runtime**: the Windows null-device cases pass at realtime priority — FL-1 and the new BUG-SWEEP-06 case
   inside `engine_tests` 26/135/0 in the gate; the desktop self-test opens "NULL Playback Device · 48000 Hz ·
   block 128", plays, saves/reopens and exports. Zero occurrences of the fallback log line in the Windows
   verbose gate log and self-test log (grep count 0 in both) — the fallback never fired on Windows.

it prove real Linux audio hardware (ALSA/JACK/Pulse) under load, or the privileged-Linux realtime path (that
branch is confirmed in code only). Per AGENTS.md: "Linux não prova runtime Windows."
